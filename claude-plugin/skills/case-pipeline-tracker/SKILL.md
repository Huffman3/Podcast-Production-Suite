# Case Pipeline Tracker

Manages a persistent production pipeline for *Who Killed…?* episodes. Every case
Bill is actively tracking — from first discovery to published episode — lives in
one file: `PIPELINE.md` in the workspace folder.

The goal is simple: Bill should always be able to ask "where does everything
stand?" and get a clear, honest answer.

---

## Pipeline Stages

Cases move through these stages in order. A case can also be **SHELVED** from
any stage.

| Stage | Meaning |
|-------|---------|
| **DISCOVERED** | Case identified as interesting, no research started yet |
| **RESEARCHING** | Active research underway (daily-case-research in progress) |
| **BRIEF COMPLETE** | Research brief done, awaiting go/no-go decision |
| **SCRIPTING** | Script being developed |
| **RECORDED** | Episode recorded, in post-production |
| **PUBLISHED** | Episode live in the feed |
| **SHELVED** | Paused indefinitely — not dead, just waiting |

---

## Operations

Determine what Bill is trying to do, then execute the right operation:

### VIEW — Show the pipeline
Triggered by: "what's in the pipeline", "pipeline status", "where does everything stand"

Read `PIPELINE.md` and render a clean summary organized by stage. Show each case
under its stage with its key details and most recent note. If the pipeline is empty,
say so and offer to add the first case.

### ADD — Add a new case
Triggered by: "add [case] to the pipeline", "put this in the pipeline", "track this one"

Collect the minimum required info (see Case Record format below). If Bill just
named a case without details, fill in what you can and flag what's missing. Append
to `PIPELINE.md` under the appropriate stage. Default new cases to **DISCOVERED**
unless Bill specifies otherwise.

If a research brief was just generated by `daily-case-research`, pull the case
name, location, year, and Podcast Potential score from that output automatically —
don't make Bill re-enter what you already know.

### UPDATE — Change a case's status or notes
Triggered by: "move [case] to scripting", "update [case]", "we recorded [case]",
"[case] is done", "add a note to [case]"

Find the case in `PIPELINE.md`, update its stage and/or notes, and add a datestamp
to the update. Confirm the change back to Bill.

### SHELVE — Pause a case
Triggered by: "shelve [case]", "put [case] on hold", "not doing [case] right now"

Move the case to SHELVED stage. Optionally record why. Cases on the shelf are
not gone — they're just waiting.

### REMOVE — Delete a case from tracking
Triggered by: "remove [case]", "drop [case] from the pipeline"

Confirm before removing. Never delete without explicit approval. After confirmation,
remove from `PIPELINE.md` and note the removal.

### EXPORT — Generate a spreadsheet view
Triggered by: "export the pipeline", "give me a spreadsheet", "pipeline as xlsx"

Read `PIPELINE.md` and generate a `.xlsx` file using openpyxl. Each case gets a
row. Columns: Case Name, Victim, Location, Year, Stage, Priority, Podcast Score,
Date Added, Last Updated, Notes. Color-code by stage (see colors below). Save to
the workspace folder.

Stage colors for xlsx export:
- DISCOVERED: light blue (#DDEEFF)
- RESEARCHING: light yellow (#FFFBCC)
- BRIEF COMPLETE: light orange (#FFE5CC)
- SCRIPTING: light purple (#EEE0FF)
- RECORDED: light green (#DDFFD8)
- PUBLISHED: medium green (#B8F0B0)
- SHELVED: light gray (#E8E8E8)

## Case Record Format

Each case in `PIPELINE.md` uses this structure:

```markdown
### [Case Name]
- **Stage**: [current stage]
- **Victim**: [name, if applicable]
- **Location**: [city, state/country]
- **Year**: [year(s) of crime]
- **Priority**: [High / Medium / Low]
- **Podcast Score**: [X/10, or — if not yet assessed]
- **Date Added**: [YYYY-MM-DD]
- **Last Updated**: [YYYY-MM-DD]
- **Notes**: [Most recent note or next action]
```

Keep notes brief and actionable. The Notes field is for the next step, not a
full history. If Bill adds a longer note, summarize it into one sentence here
and keep the original in conversation.

---

## PIPELINE.md Structure

The file is organized by stage, with a header and a summary count:

```markdown
# Who Killed…? Case Pipeline
Last updated: [date]

**Pipeline Summary**: X cases total — Y in active production, Z shelved

---

## DISCOVERED
[case records]

## RESEARCHING
[case records]

## BRIEF COMPLETE
[case records]

## SCRIPTING
[case records]

## RECORDED
[case records]

## PUBLISHED
[case records]

## SHELVED
[case records]
```

If a stage has no cases, include the header but write "*(none)*" beneath it.
This makes it easy to scan the full pipeline at a glance.

## Where the file lives

Always read from and write to:
`/sessions/zealous-inspiring-babbage/mnt/Who Killed Podcast Guidelines/PIPELINE.md`

If `PIPELINE.md` doesn't exist yet, create it with the full structure above
before doing anything else. Pre-populate PUBLISHED with:
- **Amy Mihaljevic** (Bay Village, OH, 1989) — Bill's first series
- **Cleveland Torso Murders** (Cleveland, OH, 1934–1938) — Bill's second series

This gives the pipeline a real starting point instead of an empty file.

---

## Tone when reporting back

Keep it practical and direct. Bill doesn't need a lot of preamble. Lead with
the information. If the pipeline has a bottleneck (e.g., four cases sitting in
BRIEF COMPLETE with nothing moving to SCRIPTING), flag it — that's useful.

If something looks off (a case has been in RESEARCHING for a long time with no
update, for example), mention it briefly. The tracker is most useful when it
surfaces things Bill might not be actively thinking about.
